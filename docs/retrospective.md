# 一页 AI 复盘：机房智能告警诊断平台

> 记录本次 AIOps 挑战中关键 AI Prompt、过程踩坑与后续优化方向。对应变更：`add-aiops-alert-diagnosis-platform`。

## 1. 关键 AI Prompt

### 1.1 根因分析 Prompt（`backend/app/diagnosis/prompts/rca_v1.md`）

设计原则：**结构化输出 + 证据约束 + 不确定性表达**，而不是"请分析一下"。

- 角色与输出：资深 SRE；只输出一个 JSON 对象，禁止 Markdown 包裹与额外解释。
- 证据约束：不得编造输入中不存在的告警/日志/节点；`evidence_alert_ids`/`evidence_log_ids` 只能引用证据集中真实存在的 id。
- 候选约束：`root_cause_category` 必须来自决策模型给出的候选类别；`root_cause_node` 必须是事件节点之一。
- 不确定性：证据薄弱时 confidence 必须低于 0.5，并在 `missing_evidence` 列出需补充的证据；需要人工确认时 `needs_review=true`。
- 版本化：Prompt 内容哈希写入每条诊断记录（`rca_v1:<hash>`），改 Prompt 即产生新版本，便于 A/B 与回溯。

关键片段：

```text
1. 只输出一个 JSON 对象，不要输出 Markdown 代码块、解释性前后缀或任何额外文本。
2. 不得编造输入中不存在的证据：事件、节点、告警、日志、指标。证据不足时降低 confidence，
   并在 missing_evidence 中列出需要补充的证据类别。
3. root_cause_category 必须从输入给出的候选类别中选择。
...
6. confidence 是 0 到 1 之间的浮点数；证据薄弱时必须低于 0.5。
```

### 1.2 报告生成 Prompt

- 先生成确定性骨架（摘要/影响/根因/证据/验证/回滚），再让模型只补"分步排查与修复步骤"，避免模型漏章节。
- 每一步必须含：动作、预期结果、风险等级、回滚动作；**重启/删除/改配置等高风险动作由规则强制标 high 并要求人工确认，模型无权降级**。
- 低置信度诊断必须使用"可能/待确认"措辞，禁止把推测表述成事实。

### 1.3 开发协作 Prompt

- 前后端并行时先冻结 `docs/api-contract.md`（路径、字段、错误体），AI 按契约实现，减少联调返工。
- 对 AI 明确写入边界（只允许哪些目录）、验证命令与验收标准，避免并行写共享文件产生冲突。

## 2. 过程踩坑记录

| # | 坑 | 现象 | 处理 |
| --- | --- | --- | --- |
| 1 | 拓扑方向语义混淆 | 按"调用方向"建边时，MySQL 故障被排到根因候选末位（上游网关反而第一） | 统一为**故障传播方向**（被依赖组件 → 依赖它的组件，入度 0 = 根因），同步修改 `config/topology.yaml`、规格与设计文档 |
| 2 | SQLite 丢失时区 | 接口返回 `2026-...T10:57:42` 无时区后缀，前后端对 UTC 的理解不一致 | 自定义 `UTCDateTime(TypeDecorator)`，写入存 naive UTC、读回补 UTC；全量测试回归 |
| 3 | 已解决聚合告警的复发 | 冷却期后新告警被当成"新聚合"，证据链断裂 | `upsert_cluster` 支持 resolved → open 重开并累加 `reopen_count`，保留原聚合标识 |
| 4 | 固定时间桶边界拆散同一故障 | 跨桶的同一规则告警生成两个聚合 | 查询当前桶时回看前一桶，且 `occurred_at - last_seen <= window` 才并入；补边界测试 |
| 5 | "去重"与"降噪"混淆 | 同一批告警既按 dedup_key 合并、又按 cluster 聚合，计数口径容易重复 | 明确两层语义：Alert 级幂等去重、Cluster 级降噪聚合；统计用 `repeat_count` 口径 |
| 6 | 回放虚拟时钟"穿越" | 为隔离批次把回放基准设为 30 天前，看板 60 分钟窗内看不到回放事件 | 改为 `now-60s` 基准 + `source=replay:<batch_id>` 隔离指纹 + 批次时间槽避让，事件回到当前窗口 |
| 7 | LLM 不可用/输出漂移 | 无密钥、超时、返回非 JSON 时诊断链路直接失败 | Schema 校验 + 一次修复重试 + 自动降级（决策模型结论 + 模板推理），Mock 模式保证演示确定可复现 |
| 8 | 评估"喂题"风险 | 内置 6 个场景 Top-1 准确率 1.0，容易高估 | 在文档中明确"只代表内置场景自洽性"；后续保留 hold-out 场景、引入真实故障回放再评估 |
| 9 | 依赖安装受限 | home 只读、PyPI 直连极慢，虚拟环境不可用 | 依赖装到仓库 `.deps` + 阿里云镜像；Makefile 自动注入 `PYTHONPATH`，README 给两种安装路径 |

## 3. 当前效果基线（演示环境、Mock 模式）

- 内置场景评估：`top1_accuracy=1.0`、`top3_accuracy=1.0`、`node_accuracy=1.0`、`avg_latency_ms≈9ms`、`avg_compression_ratio≈3.0`。
- 突发注入演示：30 条同源告警 → 1 个故障事件（30× 压缩），诊断 ~数十毫秒返回，报告 4 个步骤。
- 说明：准确率为内部场景自洽结果，不代表真实机房泛化能力；压缩比随注入规模变化。

## 4. 后续优化方向

1. **真实数据接入**：Prometheus/Alertmanager、ELK/Loki 适配器；Webhook 之外补充 OpenTelemetry。
2. **诊断增强**：历史故障向量检索（相似事件 Top-K 作为 RAG 证据）；将评估数据用于学习排序器；引入拓扑权重与时序因果检验。
3. **评估体系**：hold-out 场景集、按故障类型分层指标、误报/漏报代价分析、人工复核闭环回流。
4. **工程化**：SSE 替代轮询；PostgreSQL + 多 worker；诊断任务队列（Celery/Redis）；报告动作审批与审计。
5. **产品化**：告警静默/抑制规则、值班排班与通知、多租户与 RBAC。
6. **Prompt 治理**：建立 Prompt 回归集，每次修改自动跑评估并对比准确率/耗时/成本。
